# G6 编队

在接收用户编队请求的主线程中使用本技能。主线程负责架构、任务拆分、共享接口、集成和最终验收。工作器负责边界明确的实现、针对性验证和自我审查。工作器是叶节点实现者，不得创建子代理或调用编队编排。

## 派发配置

每次调用 `spawn_agent` 时都使用以下值。此配置块是工作器配置的唯一权威来源：

```json
{
  "agent_type": "worker",
  "model": "gpt-6-luna",
  "reasoning_effort": "xhigh",
  "fork_turns": "none"
}
```

为每个工作包添加唯一的 `task_name` 和自包含的 `message`。派发前，检查运行时可用的模型、推理级别、协作工具和活跃代理。如果此配置不可用，请报告确切限制；仅在继续执行确有必要时请求更换模型。不得静默替换模型或省略覆盖配置。

本技能不设工作器总数或固定并发上限。根据任务规模、独立工作包和依赖关系决定所需工作器数量；实际并发遵守运行时公布的容量，并计入主线程及其他代理的占用。容量允许时派发所有已就绪且写入所有权互不冲突的工作包；容量不足时排队，按依赖顺序随可用容量继续调度。可以复用已有工作器执行后续工作包；仅使用运行时明确提供的生命周期能力管理容量，不假定工作器交付或空闲就会释放槽位。

## 规划并分配所有权

检查适用的仓库指令、相关源码、用户已有变更和验证命令。将请求转化为验收标准、约束条件和边界明确的工作包。派发前，每项验收标准都必须有负责人和验证方法。

选择最小且有实际价值、写入所有权相互独立的工作包。将耦合的编辑放在同一工作包中，或安排在依次执行的不同批次中。在依赖项开始实现前确定共享接口。跨工作包的设计决策和最终集成由主线程负责。

任何文件或模块在同一时间只能由一个写入者负责，包括共享配置、锁文件和生成产物。工作器可以读取其写入范围之外的相关文件。告知每个工作器：它与其他任务共享工作区，必须保留用户及同级工作器的变更。执行提交、推送、重置、丢弃变更和破坏性 Git 操作前，必须获得用户对相应操作的明确授权。

规划的详细程度应与工作规模相称。小型工作包可以使用简短的派发消息；当依赖关系或风险需要时，应详细说明架构、失败场景和接口契约。无论工作包大小，都要明确写出必需信息。

## 提供自包含的工作包

工作器从空白对话开始。每条派发消息都必须包含：

- **角色与结果：** 叶节点实现者、面向用户的目标、验收标准，以及与该工作包相关的重要范围排除项。
- **所有权：** 可写入的确切路径或模块、必须保留的现有变更、依赖项和共享接口契约。
- **项目指令：** 从仓库根目录到所负责路径之间所有适用的 `AGENTS.md`，以及必读的引用文档和对话中提供的相关指令。要求工作器在编辑前阅读适用文档。
- **技能：** 以 `$codebase-memory` 等可移植逻辑名称列出必需技能，并说明每项技能适用的原因。工作器从自身的可用技能目录中解析名称，完整阅读技能所公布的 `SKILL.md`，继续读取其中指向的引用，并酌情选择其他执行技能。编队编排始终留在主线程。
- **能力：** 必需的工具能力、首选实现和允许的备选方案。工作器应检查本地可用及可发现的工具，在不假定存在某个特定机器可执行文件或 MCP 服务器的前提下满足各项能力要求。缺少硬性要求即构成阻塞；首选实现可以替换为获准的等效方案。安装、连接或重新配置工具需要用户授权。
- **既有证据：** 相关路径和符号、已确认的行为、既定决策、已运行的检查和尚未解决的问题。复用证据，同时重新核对可能受新编辑影响的假设。使用代码图时，应传递项目、生成情况/新鲜度、覆盖情况、相关查询结果和分页状态，以及已执行的源码回退检查；遵循代码图技能的验证要求。
- **验证：** 有意义的针对性检查、适用的质量门禁，以及留待最终集成阶段执行的检查。需要证明行为变更时，应添加或更新测试；验证规模应与变更及仓库要求相称。
- **交付：** 下方的报告格式、所有权移交规则，以及及时报告阻塞项的要求。

项目材料使用仓库相对路径，已安装的技能使用逻辑名称。笼统要求“遵循约定”不能替代适用的指令和能力清单。工作器必须报告自己实际加载和解析的内容。

## 协调工作并从阻塞中恢复

只派发前置条件已经确定的工作包。跟踪每个工作包的负责人、依赖项、状态、验证证据和未决风险。工作器运行期间，继续开展有价值的设计或集成准备。如果没有可独立推进的工作，应使用既能维持及时用户更新、又可避免频繁轮询的等待方式。

如果工作器需要修改接口、改动其他负责人所有的文件或补充缺失能力，应报告确切需求及其影响，然后继续执行其范围内的独立工作。主线程负责解决依赖、将变更分配给其负责人，或明确移交所有权。

只有在上一位写入者已经完成工作或确认停止编辑后，才能移交所有权。交付报告意味着工作器结束对该工作包的写入活动；后续编辑需要再次分配任务。如果工作器崩溃或无响应，应先停止该工作器并核实其状态，再重新分配其文件。检查残留的部分变更并保留有用工作。

如条件允许，复用原工作器执行边界明确的修正。如果针对同一原因进行一次澄清后的重试仍然失败，应检查实际证据，并由主线程接手修正或报告具体阻塞。避免反复盲目重试。

## 工作器交付门禁

报告完成前，工作器必须已经加载适用的指令和技能、满足必需的能力、完成其所有范围内的实现、运行适当检查，并检查自身差异中的正确性、边界情况、兼容性和意外编辑。修复自我审查发现的问题，或逐项披露尚未解决的问题。明确区分通过的检查、失败的检查和无法运行的检查。

使用以下契约返回简洁报告；适当时填写 `none`：

```text
状态：complete | partial | blocked
已加载的指令和技能：
已满足的工具/能力及备选方案：
变更的文件：
实现和验收证据：
检查：确切命令、结果和未运行的检查
自我审查发现及修复：
剩余风险或阻塞项：
主线程审查重点：
所有权：已停止编辑，等待后续任务
```

## 集成与验收

检查每个工作包在工作区中的实际变更和验证证据。工作器报告为审查提供信息；主线程独立判断完整实现是否满足请求。

核实指令和技能的加载情况、能力满足情况、所有权边界、现有变更的保留情况，以及每项验收标准。协调工作包之间的交互、公共接口、错误路径、重要失败场景和工作器尚未解决的发现。共享设计的取舍由主线程决定。

将工作器运行的检查视为其已测试状态的证据。运行必需的最终质量门禁，以及能够证明集成行为的检查。如果集成变更使先前结果失效，则重新运行针对性检查；没有具体理由时，避免在状态未变的情况下重复执行昂贵检查。

对于高风险变更，可以安排一个可用工作器在实现完成后执行边界明确的只读对抗性审查。最终验收仍由主线程负责。

只有所有验收标准均已满足且必需检查均已得到说明，任务才算完成。报告最终实现的行为、执行过的验证和重要的剩余限制。如果任务受阻或仅部分完成，应准确说明剩余工作，不得宣称成功。
